# Packaging

How the macOS app (Apple Silicon, arm64, built locally) and the Linux app (x64 AppImage and deb, built in CI, see [[#Linux (x64)]]) are built from the repo with [electron-builder](https://www.electron.build/). Personal use: no signing identity, no notarization. Updates: the app updates itself from the GitHub Releases ([[#Updates]]). Releases: [[#Releases]]. Context: [[Attribution and Licenses]] (what must travel with the app), [[SPEC]].

> [!info] No license key
> The Design Canvas runs on React Flow (MIT), so a package needs no license key, secret or environment variable to build. The history of the tldraw key is in [[tldraw|the tldraw spike]]. See [[#Smoke test]] for the automated check of a package.

## Build

Prerequisites: macOS on Apple Silicon, Node.js 22.18 or later, `npm ci` done, and the Electron binary installed (`npx install-electron`, run by `npm run dev` and `npm run preview`). No network is needed once Electron and the dmg tooling are in place.

```bash
npm run package       # electron-vite build, electron-builder (.app + .dmg), then the guard script
npm run package:dir   # same without the .dmg (faster, for checking the .app)
```

Output in `dist/` (git-ignored):

| Path | What |
|---|---|
| `dist/mac-arm64/System Design from Scratch.app` | The app, about 360 MB (Electron itself is most of it). |
| `dist/system-design-from-scratch-<version>-arm64.dmg` | Disk image with the app and an Applications shortcut, about 130 MB. |

The config is `electron-builder.yml`. Notes on the choices:

- `electronDist: node_modules/electron/dist`: the Electron already installed is packaged, nothing is downloaded for it. electron-builder still downloads its dmg tooling (`dmgbuild-bundle`) once, on the first `.dmg` build, into its cache; later builds are offline.
- `identity: "-"`: the whole bundle is signed ad hoc (no certificate, hardened runtime off) after electron-builder has added `app.asar` and edited `Info.plist`. Without it the bundle keeps Electron's own ad-hoc seal, which no longer matches the edited content: `codesign --verify` fails ("code has no resources but signature indicates they must be present") and a copy with the quarantine attribute opens as "damaged" on macOS 26 (seen on the `v0.1.0` download, fixed in #45). `scripts/check-package.mjs` runs `codesign --verify --deep --strict` on the app.
- `npmRebuild: false`: the app has no native module (`node:sqlite` is built into Electron's Node).
- `publish: null`: no update feed (`latest-mac.yml`) is generated: updates do not use `electron-updater` ([[#Updates]]).
- The icons are generated by `npm run icon:build` (`scripts/build-icon.mjs`, run with Electron): the brand mark of the app header on a dark rounded square. It writes `build/icon.icns` (macOS, needs `iconutil`, so macOS only) and `build/icons/<size>x<size>.png` for 16, 24, 32, 48, 64, 128, 256 and 512 px (Linux). Rerun it and commit the result only when the design changes.

## What is in the package

`app.asar` holds `package.json`, `out/` (the electron-vite output: main, preload and the renderer with its inlined fonts) and `resources/` (`corpus/primer.json`, `licenses.json`). Nothing else: no `src/`, `docs/`, `spikes/`, `screenshots/`, `scripts/`, tests, `.env*`.

The app ships no `node_modules`. The renderer is bundled by Vite, and the main process bundle includes its only runtime package, `zod` (`electron.vite.config.ts`, `externalizeDeps.exclude`). A package added later to the main or preload side must be bundled too, or the guard script fails.

Outside the asar, in `Contents/Resources/`:

- `LICENSES.chromium.html`: the Chromium, Node.js and other notices that Electron distributes. Electron ships it next to `Electron.app`, not inside it, and electron-builder does not copy it into a macOS app, so `extraResources` does.
- `LICENSE.electron`: Electron's own MIT license.

### Guard script

`scripts/check-package.mjs [--platform mac|linux] [--app-only]` runs at the end of `npm run package` (macOS, the default platform) and `npm run package:linux`, and exits 1 when:

- `LICENSES.chromium.html` or the Electron license is missing from the `.app` (`Contents/Resources`) or, on Linux, from `dist/linux-unpacked/resources/`;
- `app.asar` lacks a runtime file (`out/main/index.js`, `out/preload/index.js`, `out/renderer/index.html`, `resources/corpus/primer.json`, `resources/licenses.json`) or contains an environment file (`.env`, `.env.local`...), a top-level `src`, `docs`, `spikes`, `screenshots`, `scripts`, `build`, `.github`, `.vitest` or `node_modules`, or a test file;
- the main or preload bundle requires a package other than Electron and Node built-ins;
- there is no `.dmg` (macOS) or no `.AppImage` or `.deb` (Linux), or one is under 50 MB (not checked with `--app-only`, used by `package:dir` and `package:linux:dir`);
- on Linux, the Electron executable or `chrome-sandbox` is missing from `dist/linux-unpacked`.

## Releases

Download page: GitHub Releases, linked from the README ([[#Download]] in the README). Issue #41.

Cut a release:

1. Bump `version` in `package.json` and `package-lock.json`, commit and push to `main`. The version must be a valid semver (`1.2.3`, no pre-release suffix on a published release) **greater than the previous release**: the app offers an update only when the latest release is a stable version strictly newer than the running one ([[#Updates]]).
2. Tag and push: `git tag v<version> && git push origin v<version>`. The tag must equal `v` plus the `package.json` version, or the workflow stops.
3. `.github/workflows/package.yml` builds both packages (Linux on `ubuntu-latest`, macOS arm64 on `macos-14`), runs the guard script and the smoke test on each, then the `release` job creates a **draft** release named after the tag with the dmg, AppImage, deb and `SHA256SUMS` attached. The notes start from `.github/release-notes.md` (install steps), followed by GitHub's generated change list.
4. Open the draft on the Releases page, read it, then **Publish**. Nothing is public before that. Publish only when the macOS `.dmg`, the Linux `.AppImage` and `SHA256SUMS` are attached: a published release without them is announced by the app, but cannot be installed in one click on that platform. The workflow also runs the AppImage on Ubuntu 22.04 (`linux-ubuntu-2204` job) before the draft is created.

A manual run (**Actions > Package > Run workflow**) only uploads workflow artifacts (`linux-x64`, `macos-arm64`, 14 days), no release. No repository secret is needed: the build reads no environment variable.

Release assets have no space in their names (GitHub rewrites spaces to dots): electron-builder's `artifactName` is `${name}-${version}-${arch}.${ext}`.

Not verified by CI: a release downloaded on a Mac carries the quarantine attribute ([[#Open an unsigned build]]); the macOS smoke test runs the app from the build folder, not from the downloaded dmg. `install.sh` ([[#Open an unsigned build]]) is tested by hand against a local dmg and the published release.

## Updates

Issues #58 (macOS) and #59 (Linux). The app checks whether a newer release exists, and installs it in one click on macOS (Apple Silicon, packaged app) and on Linux x64 when it runs as an AppImage; a `.deb` install, or any other run, shows a banner with a link to the release page (no automatic install). Vocabulary: [[App Update]]. The Linux install is described in [[#Linux updates (AppImage)]].

### How it works

1. **Check.** At launch (once a day at most, unless **Settings > Updates > Check for updates at launch** is off; the result of the last check is kept in the `settings` table) and from the **Check for updates** button, the main process reads `https://api.github.com/repos/jbclaramonte/system-design-from-scratch/releases/latest` and compares the tag with the running version (semver, `src/main/update/version.ts`). Only a stable release strictly newer than the running version counts; drafts and pre-releases are never offered. A network error is shown as a readable message by the button and is silent at launch: the app is never blocked. A development build (`npm run dev`) never checks on its own.
2. **Banner.** "Version X is available" with **Install and restart**, **Not now** and a link to the release notes. **Not now** remembers the version (`update_dismissed_version`): it is not announced again, a newer version is, and the button of Settings shows it again. The banner does not appear during a Quiz round or on a Design Exercise screen (the learner finishes first; the banner returns when they leave).
3. **Install** (`src/main/update/installer.ts`), the steps of `install.sh`: download the `.dmg` and `SHA256SUMS` of that release into a temporary folder, check the checksum, `hdiutil attach -readonly`, `ditto` the app to a hidden staging folder **next to the running app** (same volume), `hdiutil detach`, `codesign --verify --deep --strict` on the copy, and check that the copy is this app (bundle id `com.jbclaramonte.system-design-from-scratch`) at the announced version. A downloaded file written by the app carries no quarantine attribute, so no Gatekeeper dialog appears.
4. **Swap** (`src/main/update/helper.ts`). The running app cannot replace itself, so the main process starts a small detached `bash` script and quits. The script waits for the app process to exit (two minutes at most), renames the old bundle to a backup next to it, renames the staged copy to the app's path (two renames in one folder: the old app is deleted only after the new one is in place, and put back if the second rename fails), clears the quarantine attribute if present, relaunches the app with the arguments and environment it had (a custom `--user-data-dir` survives) and removes the backup and its temporary folder. Its steps are logged in `$TMPDIR/sdfs-update.log` (one small file, overwritten at each update).
5. **Failure.** Any step before the quit (download, checksum, mount, copy, signature, identity) leaves the installed app untouched, removes what it created and shows the reason with the manual download link. A failure in the helper puts the old app back and relaunches it.

The install is **refused**, with the reason and the manual download link, when the app is not packaged, does not run from an `.app` bundle path, its folder is not writable for the learner (for example an app in `/Applications` owned by another user: move it to `~/Applications`), or the machine is neither macOS arm64 nor Linux x64 (below). The app data folder is never touched by an update.

### Linux updates (AppImage)

Issue #59. The same flow (check, banner, **Install and restart**, quit, relaunch), with the steps of `install.sh` on Linux, in `src/main/update/appImageInstaller.ts` and `appImageHelper.ts`, built from the same injectable pieces as the macOS one (release lookup, HTTP download, checksum) plus a few Linux ones.

1. **Which file to replace: the `APPIMAGE` variable.** The AppImage runtime sets `APPIMAGE` in the environment of the app to the path of the `.AppImage` file that runs (also when it extracts and runs). The app uses that path, with symbolic links resolved (the file behind a link is replaced, not the link), and requires a regular file in a folder the learner can write. Without `APPIMAGE` (a `.deb` install, `dist/linux-unpacked`, `npm run dev`) the banner only links to the release page: a `.deb` is updated with `apt`, which needs administrator rights, so the app never tries.
2. **Install** (the steps of `install.sh`): download the `system-design-from-scratch-<version>-x86_64.AppImage` and `SHA256SUMS` of the release, the AppImage into a hidden file **next to the running one** (same folder, hence one volume), check its checksum, `chmod 755`.
3. **Replace.** The detached relaunch helper (a small `bash` script, logged in `$TMPDIR/sdfs-update.log`) is started first, so that a failure to start it replaces nothing. Then one `rename(2)` puts the new file at the path of the running one. It is atomic, and safe under a running instance: the AppImage runtime keeps the old file open (its mount and its inode), the running app is not affected. If the rename fails, the helper is stopped and the staged file removed.
4. **Relaunch.** The app quits (half a second later). The helper waits for it to exit (two minutes at most; after that it gives up without relaunching, the update stays installed for the next start), then starts the new AppImage detached, in the folder the app was started in (`OWD`, set by the runtime), with the **arguments** of the running app (a custom `--user-data-dir` survives) and its **environment**, minus `APPIMAGE`, `APPDIR`, `ARGV0` and `OWD`, which the runtime of the new file sets again (`APPIMAGE_EXTRACT_AND_RUN` and the rest are kept).
5. **Failure.** Any step before the rename (download, checksum, `chmod`, helper) leaves the installed file untouched, removes what it created and shows the reason with the manual download link. A release without the AppImage or `SHA256SUMS` is announced, with the release page link instead of the install button.

Trust level: **the same as on macOS and as `install.sh`**: TLS to GitHub and a checksum from the same release as the file (it protects against a corrupt download, not against a compromised release or account), and no signature of the author (the AppImage is not signed). `APPIMAGE` is read from the environment of the app; anyone who can set it can already run code as the user. The renderer is unchanged (CSP `connect-src 'self'`).

### Why not electron-updater

On macOS `electron-updater` relies on Squirrel.Mac, which only installs a build signed by **the same identity** as the running app. The app is signed ad hoc (`identity: '-'`, #45): the signature is tied to each build's exact content, so every update would be refused. A Developer ID certificate and notarization (99 USD a year) were declined, so the update is done by the app itself with the steps of `install.sh`. No `latest-mac.yml` feed is generated (`publish: null`).

### Trust level

- The update is as trustworthy as `install.sh`: TLS to GitHub, and a checksum **from the same release** as the image. The checksum protects against a corrupt or truncated download, **not against a compromised release or GitHub account**: whoever can replace the `.dmg` can replace `SHA256SUMS`. The ad-hoc signature is checked for integrity (the seal matches the bundle), not for the author's identity. A possible follow-up: sign `SHA256SUMS` with a project key whose public half ships in the app.
- The only requests are the release lookup, then the two downloads of an install; HTTPS only (HTTP is accepted only to this machine, for the tests), and a redirect to an insecure address is refused. No identifier, version or telemetry is sent beyond what any HTTP request carries (a fixed `User-Agent`).
- The renderer is unchanged: its CSP stays `connect-src 'self'`, every request is made by the main process.
- The two environment variables below are read at launch; anyone who can set the environment of the app can already run code as the user.

### Test overrides

| Variable | Meaning |
|---|---|
| `SDFS_UPDATE_API_URL` | Replaces the release lookup address: a URL that answers the GitHub "latest release" JSON (`tag_name`, `html_url`, `assets`). |
| `SDFS_UPDATE_DOWNLOAD_BASE_URL` | Folder URL that holds the `.dmg`, the `.AppImage` and `SHA256SUMS`, instead of the asset addresses of the release (like `BASE_URL` in `install.sh`). |

Setting either one also turns the check at launch on for a development build. Unit tests never use the network: the HTTP client, the commands (`hdiutil`, `ditto`, `codesign`, `plutil`), the file operations of the Linux install (`chmod`, `rename`), the helper launches and the quit are injected. The two helper scripts are run for real (`bash`, scratch folders) by their tests, and the AppImage installer is also run once against the real relaunch helper. The smoke test starts a local fake release server and points the packaged app at it ([[#Smoke test]]).

### Checked by hand (#58)

Two packaged builds were made in a scratch folder (`electron-builder -c.directories.output=<scratch>`, version 0.3.1 through `-c.extraMetadata.version=0.3.1`, the repo's `package.json` untouched), served by a local fake release, and the 0.3.0 app was run from a scratch install folder with a scratch `--user-data-dir` (never `/Applications`, never the real data folder):

- install: the banner offered 0.3.1, **Install and restart** quit the app, the helper swapped the bundle, the relaunched app reported 0.3.1 (same `--user-data-dir`), its signature was valid, there was no quarantine attribute, and the temporary folder and the hidden folders next to the app were gone;
- bad checksum: the install stopped with the corruption message, the app kept running at 0.3.0, the installed bundle was unchanged and nothing was left behind.

Not exercised: a real release on GitHub, an app in `/Applications`, a quarantined (browser-downloaded) first install, a learner on another user account, a full disk, and the Linux banner on a real desktop.

### Checked for Linux (#59)

On macOS, against local fake releases only (scratch `HOME`, scratch install folders, no GitHub):

- `install.sh`, Linux branch, through `SDFS_TEST_PLATFORM`: `scripts/test-install.sh` (install, executable bit, launcher content, icon, second run replaces the first, running instance refused, checksum mismatch, FUSE 2 missing, `INSTALL_DIR` with a space, `XDG_DATA_HOME`, unsupported platforms), and the macOS branch for real with an ad hoc signed fake app in a `.dmg` (no regression);
- the same script for real on Ubuntu 24.04 and Ubuntu 22.04 containers (x64, emulated, non-root, scratch `HOME`): the `/proc` check of a running instance and `libfuse` detection ran there, not on macOS;
- the updater: unit tests with fakes (see the issue for the list), the relaunch helper and the installer run for real, and the packaged app's whole AppImage update in the smoke test ([[#Smoke test]]), run against the packaged `app.asar` on the Linux Electron binary in an Ubuntu 22.04 container.

Not exercised: a real AppImage replaced while it runs (the real runtime and FUSE mount; the smoke test replaces a scratch file standing for it), a launcher on a real desktop (GNOME, Wayland, icon rendering, the application menu entry), a real release on GitHub, and the first CI run of the new jobs.

Hand-check list for the first Linux user (Ubuntu 22.04, x64, GNOME), not covered by any test:

1. Run the install one-liner on the machine: the AppImage and the launcher are installed, and **System Design from Scratch** is in the application menu with its icon (look at the icon in the menu and in the window switcher; on Wayland the window should group under the launcher).
2. Start it from the menu. If it does not start, run the AppImage from a terminal and read the error (FUSE 2? sandbox?).
3. Set the Claude Code CLI path in **Settings** if needed, then generate the first lesson.
4. With a newer release published: **Settings > Updates > Check for updates**, then **Install and restart**. The app must quit and come back on the new version (About shows it), from the same launcher.
5. Run the install command a second time while the app is open: it must refuse and ask to quit the app.

## User data

The packaged app uses the same folder as `npm run dev` and `npm run preview`: `~/Library/Application Support/system-design-from-scratch/` on macOS, `~/.config/system-design-from-scratch/` on Linux (`$XDG_CONFIG_HOME` when set; the SQLite database `system-design-from-scratch.db`, caches). The folder is named after the package name, not the product name ("System Design from Scratch"), so `src/main/index.ts` sets `userData` explicitly at startup unless a `--user-data-dir` switch is given (tests and verification runs use a scratch folder that way). Existing data is reused as is; a packaged app enforces the Learning Path locks that dev builds skip (`app.isPackaged`).

The app still needs the Claude Code CLI at runtime (see the README). An app opened from Finder (macOS) or from a Linux application menu or `.desktop` launcher does not see the shell PATH: it looks in the common install locations (`~/.local/bin`, `~/.claude/local`, Homebrew and Linuxbrew, `/usr/local/bin`, `~/.npm-global/bin`) and then asks a login shell (`$SHELL`, else bash on Linux). Set the CLI path in **Settings** if `claude` is still not found.

## Open an unsigned build

The app is signed ad hoc and not notarized (no Apple Developer ID, which costs 99 USD a year). macOS treats a file with the `com.apple.quarantine` attribute as untrusted, and only a browser, AirDrop or a messaging app set it.

- **A package built locally** has no quarantine attribute: drag the `.app` to `/Applications` (or open the `.dmg` and drag it onto the Applications shortcut), then open it.
- **Install script (recommended for a release)**: `install.sh` at the repo root downloads the release `.dmg` and `SHA256SUMS` with `curl`, which sets no quarantine attribute, checks the checksum, mounts the image, verifies the app signature, copies the app to `INSTALL_DIR` (default `/Applications`) through a staging folder and unmounts. It refuses to install when the signature is invalid (the `v0.1.0` release has an invalid one: use `VERSION=v0.1.1` or later). It never touches the data folder. `BASE_URL` (a folder with the dmg and checksums, `file://` works) is for tests.
- **A copy from a browser, AirDrop or a message** is quarantined. Since the signature is valid, macOS shows the usual "cannot verify the developer" dialog. On macOS 15 and later right-click > **Open** no longer bypasses it: open **System Settings > Privacy & Security**, scroll to the blocked app, **Open Anyway**. Or remove the attribute with the full path to the system tool (a `xattr` earlier in `PATH`, such as a pyenv shim, may not support `-r`):

```bash
/usr/bin/xattr -dr com.apple.quarantine "/Applications/System Design from Scratch.app"
```

The `v0.1.0` dmg has an invalid signature (found after publishing): downloaded in a browser it opens as "is damaged and can't be opened", and only the `xattr` command above opens it.

## Chromium license requirement

Chromium and the other bundled components require their license notices to be kept in every distribution. Electron provides them as `LICENSES.chromium.html`. Never strip it from a package; the guard script enforces it. The About screen lists the npm packages ([[Attribution and Licenses]]); this file covers Chromium and Node.js.

## Rebuild after a change

1. `npm run licenses:check` (after a `package-lock.json` change, `npm run licenses:build` first).
2. `npm run package`.
3. `npm run smoke:packaged` ([[#Smoke test]]).
4. Replace the app in `/Applications` (quit it first). The data folder is untouched. For the first run of a new package, follow the [[#First launch checklist]].

To try a build without touching your data, launch the binary with a scratch folder: `"dist/mac-arm64/System Design from Scratch.app/Contents/MacOS/System Design from Scratch" --user-data-dir=/some/scratch/dir`.

## Smoke test

`npm run smoke:packaged` (`scripts/smoke-packaged.mjs`, plain Node, no dependency) drives the packaged app the way a Finder launch would, as far as a script can. It is platform aware: on macOS it runs `dist/mac-arm64/System Design from Scratch.app`, on Linux `dist/linux-unpacked/system-design-from-scratch` (under `xvfb-run -a`, see [[#Linux (x64)]]). Run it after `npm run package`, `package:dir`, `package:linux` or `package:linux:dir`; it takes about 15 seconds. Options: `--app <binary>` (another build), `--shots <dir>` (keep the screenshots, default: inside the scratch folder), `--keep` (keep the scratch folder), `--no-sandbox` (Linux, see below), and `SMOKE_VERBOSE=1` (print the console messages of the canvas screen).

How it runs:

- The app binary is spawned with `--remote-debugging-port=<free port>`, a scratch `--user-data-dir` (always passed, so the real user data is never opened) and a **minimal environment**: `PATH=/usr/bin:/bin`, no `SHELL`, `HOME` set to a scratch folder, and the two `SDFS_UPDATE_*` variables that point the update check at a local fake release ([[#Updates]]) (on Linux, `DISPLAY` and `XAUTHORITY` are passed through: Chromium needs a display). The real user data and `~/.claude*` are never touched.
- A fake Claude Code CLI sits in `<scratch HOME>/.local/bin/claude`. It speaks the stream-json protocol the app expects (`--version`, `auth status`, a Notion Outline, a lesson with a Mermaid flowchart) and logs every call. As `claude` is not on PATH, finding it proves the discovery through the common install locations (`commonCliLocations` in `src/main/generation/resolveCli.ts`) and the stream-json plumbing of a packaged app.
- The page is driven over the Chrome DevTools protocol (the WebSocket built into Node 22+).
- Two launches share one scratch user-data folder. The first starts on a fresh folder. Then the app is stopped, every topic is marked mastered in the scratch database (with `node:sqlite`; the app cannot be imported here, so the script inserts a passed round per topic, the way the earlier seed scripts did) and the app is launched again, because a packaged app enforces the Learning Path lock and an exercise opens only when its prerequisites are mastered.
- The whole process group of the app is killed at the end, also on failure or Ctrl+C. The script exits 1 when a check fails and prints one `PASS`/`FAIL` line per check.

Covered:

| Check | What it proves |
|---|---|
| Window loads, `file:` origin | The packaged renderer starts, the preload bridge works. |
| Learning Path shows 21 topics | The Source Corpus is read from the package (`resources/corpus/primer.json` in the asar). |
| Database created and migrated | Scratch folder has `system-design-from-scratch.db` at the latest schema version, 21 topics and the Design Exercises seeded. |
| Settings, Test button | The screen renders, the CLI is found in `~/.local/bin` without PATH, version and login state shown. |
| About | `licenses.json` is readable (more than 50 entries) and the primer attribution renders. |
| Fonts | Geist is loaded (`document.fonts`), the fonts inlined in the bundle work from `file://`. |
| First lesson | Generated by the fake CLI through the packaged main process, displayed, the CLI got the request. |
| Mermaid diagram | The lesson's flowchart is rendered as SVG (no fallback to the source). |
| Update check | Against a local fake release (never GitHub): the launch check shows the banner with **Install and restart** (macOS) or the release page link (Linux, no `APPIMAGE`), Settings **Check for updates** reports it, **Not now** hides it, and the second launch announces nothing and makes no request (once a day). |
| Version | About shows the version of `package.json` (the packaged app reports its own version). |
| AppImage update (Linux only, third launch) | With `APPIMAGE` pointing at a scratch file: the banner offers **Install and restart**, the install downloads the fake release's AppImage, checks its checksum, replaces the scratch file (executable, no leftover next to it), the app quits and the new file is started with `--user-data-dir` and the environment of the app. |
| Exercise canvas | After the topics are mastered, the first exercise opens on its Design Canvas (React Flow), a typed component can be added, and the fonts are loaded. |
| Console | No console error, on the first launch and on the canvas screen (since #43 there is no tracking request to tolerate). |

Not covered, to check by hand ([[#First launch checklist]]):

- **The real Claude Code CLI**: login, models, real latency and output, the Claude config directory. The fake CLI proves the plumbing, not the content.
- **The real network**: the renderer fetches nothing (the CSP forbids it) and the update check only talks to a local fake release; GitHub is never called. On macOS no update is installed (that is done by hand, [[#Checked by hand (#58)]]); on Linux the AppImage update runs against a scratch file, not a real AppImage.
- **Gatekeeper and quarantine on a downloaded copy**: the locally built `.app` has no quarantine attribute, and the browser download path (**Open Anyway**) is not exercised by CI or by the script ([[#Open an unsigned build]]).
- **A launch through LaunchServices** (Finder, Dock, `open`): the script starts the binary directly, with an environment that imitates it. launchd's own environment, the app icon, the window state and the single-instance behavior are not exercised.
- The `.dmg` itself (never mounted), the copy in `/Applications`, Intel Macs, light mode, and the quality of the generated French content.

A failure keeps the scratch folder and prints its path and the app output.

## First launch checklist

For the first run of a new package on your Mac (after `npm run package` and a passing `npm run smoke:packaged`):

1. Quit the running app if any. Copy `dist/mac-arm64/System Design from Scratch.app` (or the `.app` from the `.dmg`) to `/Applications`, replacing the old one. If the copy came from a download or a message, clear the quarantine attribute first ([[#Open an unsigned build]]).
2. Open it from `/Applications` (Finder or Spotlight, not from a terminal: that is the case the smoke test cannot reproduce). The Learning Path shows 21 topics and your previous progress.
3. **Settings**: leave the CLI path empty and press **Test**. Expect the CLI version, its path and your login state. If it says `claude` is not found, set the path (`which claude` in a terminal) and test again.
4. Open an unlocked topic and read one generated **lesson** to the end: text streams in, a Mermaid diagram renders.
5. Take one **quiz round**: answer a few questions, including a free answer if the round has one.
6. During the round, press the **Lesson** button: the lesson opens and closes without losing the round.
7. **Design exercise**: once the prerequisites of Pastebin are mastered, open it, go to **High-level design**, add a component with the palette, and leave the screen open for more than 5 seconds: the canvas must stay and keep working. The exercise stays locked until its topics are mastered, so this step may have to wait; do not edit your real database to unlock it.
8. **About**: the primer attribution and the third-party licenses are listed.

## Linux (x64)

The Linux app is an AppImage and a `.deb` for x64, built by GitHub Actions on an Ubuntu runner (`.github/workflows/package.yml`), never cross-built from macOS: the Electron binary packaged is the one in `node_modules`, which is the Linux one only on a Linux host. Unsigned, personal use (issue #40). The AppImage updates itself in one click and `install.sh` installs it ([[#Linux updates (AppImage)]], [[#Install]], issue #59); the `.deb` only announces a new release ([[#Updates]]). Oldest supported release: **Ubuntu 22.04** ([[#glibc and Ubuntu 22.04]]).

### Build in CI

Run **Actions > Package > Run workflow** on GitHub (or `gh workflow run package.yml`), or push a `v*` tag. The workflow has read-only permissions and, for Linux, two jobs: `linux` on `ubuntu-latest`, and `linux-ubuntu-2204` on `ubuntu-22.04` ([[#glibc and Ubuntu 22.04]]). The `linux` job:

1. `actions/checkout`, `actions/setup-node` (Node 24, npm cache) and `npm ci`, the same pinned versions as `ci.yml`.
2. System libraries (`apt-get`): `xvfb` and `xauth` (virtual display), `libfuse2t64` (runs an AppImage without extracting it), `binutils` (`ar`, needed by the deb builder), and what the Electron binary links against: `libnss3`, `libgtk-3-0t64`, `libatk1.0-0t64`, `libatk-bridge2.0-0t64`, `libcups2t64`, `libgbm1`, `libasound2t64`, `libdrm2`, `libxss1`, `libxtst6`, `libxkbcommon0`, `libxcomposite1`, `libxdamage1`, `libxfixes3`, `libxrandr2`, `libpango-1.0-0`, `libcairo2`, `xdg-utils`. Most are already on the runner image; the names are the Ubuntu 24.04 ones (`t64` suffix).
3. `npm run package:linux`: `install-electron` (downloads the Electron binary, `npm ci` does not), `electron-vite build`, `electron-builder --linux --x64`, the guard script (`node scripts/check-package.mjs --platform linux`). The guard script runs once more as its own step.
4. The sandbox helper step ([[#Chromium sandbox]]).
5. `xvfb-run -a npm run smoke:packaged -- --shots smoke-shots` ([[#Smoke test]]): the app launched from `dist/linux-unpacked` on a virtual display, with the minimal environment and the fake CLI.
6. `scripts/check-glibc.sh dist/linux-unpacked 2.35`: lists the glibc symbol version each ELF file of the package needs (`objdump -T`) and fails when one is above Ubuntu 22.04's.
7. `scripts/test-install.sh` with `SDFS_TEST_APPIMAGE` set to the AppImage just built: `install.sh` on Linux **for real** (no platform switch), against a local release folder made of that AppImage and a `SHA256SUMS`, in a scratch `HOME`: install, executable bit, launcher content, the icon taken out of the real image, a second run replacing the first, a running instance refused, checksum mismatch, FUSE 2 missing.
8. `actions/upload-artifact`: the artifact `linux-x64` holds `dist/*.AppImage` and `dist/*.deb`, kept 14 days. If the smoke test fails, the screenshots go up as the artifact `smoke-shots` and the packages are not uploaded.

Download the files from the run page (**Artifacts**), or `gh run download <run id> -n linux-x64`.

### Build on a Linux machine

`npm ci`, then `npm run package:linux` (or `npm run package:linux:dir` for `dist/linux-unpacked` only, no installable). Needs Node 22.18+, the libraries above for the smoke test, and `binutils` for the `.deb`. electron-builder downloads its AppImage runtime (`appimage-*.7z`) and the fpm bundle (`.deb`) once into its cache. The fpm bundle it downloads for the `.deb` is an x64 build (not tried on an arm64 host).

Output in `dist/`:

| Path | What |
|---|---|
| `dist/system-design-from-scratch-<version>-x86_64.AppImage` | AppImage, about 130 MB. |
| `dist/system-design-from-scratch-<version>-amd64.deb` | Debian package, about 105 MB. |
| `dist/linux-unpacked/` | The unpacked app: executable `system-design-from-scratch`, `chrome-sandbox`, `resources/app.asar`. |

### Config notes (`linux` in `electron-builder.yml`)

- Targets `AppImage` and `deb`, x64 only; category `Education`; the same `files` rules as macOS (the asar holds `package.json`, `out/`, `resources/`, no `node_modules`).
- `artifactName` is `${name}-${version}-${arch}.${ext}`, so the file names have no space (a `.deb` is installed with `apt install ./<file>`, a name with spaces is awkward). The macOS name keeps the product name.
- Licenses: `extraResources` copies `LICENSE.electron` and `LICENSES.chromium.html` into `resources/`, as on macOS, and the guard script requires them there. The Electron distribution also leaves `LICENSES.chromium.html` and `LICENSE.electron.txt` next to the executable; electron-builder keeps them, so the package holds both copies (about 20 MB more).
- Icons: `build/icons/*.png`, from `npm run icon:build` ([[#Build]]). The deb installs them in the `hicolor` theme and a `.desktop` file (`Name`, `Categories=Education`, `StartupWMClass=system-design-from-scratch`).
- `package.json` carries what the Linux targets read: `homepage` (the deb builder refuses to run without it), `author` (name only: an email is not required, the deb `maintainer` is set in the yml), and `desktopName` with `linux.syncDesktopName: true`, so that Electron's window class matches the `.desktop` file and the launcher groups the window under its icon.
- The `.deb` installs in `/opt/System Design from Scratch/` (the product name, with spaces), links `/usr/bin/system-design-from-scratch`, depends on `libgtk-3-0`, `libnss3`, `libxss1`, `libxtst6`, `libatspi2.0-0`, `libsecret-1-0` and a few more, and recommends `libappindicator3-1`.

### Install

The one-liner (the same `install.sh` as macOS; it detects Linux x64):

```bash
curl -fsSL https://raw.githubusercontent.com/jbclaramonte/system-design-from-scratch/main/install.sh | bash
```

`install.sh` on Linux (issue #59), with `VERSION`, `INSTALL_DIR` and `BASE_URL` as on macOS: downloads `system-design-from-scratch-<version>-x86_64.AppImage` and `SHA256SUMS`, checks the checksum, installs the file as `~/.local/share/system-design-from-scratch/system-design-from-scratch.AppImage` (or in `INSTALL_DIR`; `XDG_DATA_HOME` is honored), executable, takes the icon out of the image (`--appimage-extract`, no FUSE needed) next to it, and writes `~/.local/share/applications/system-design-from-scratch.desktop` (`Exec` with the quoted path, `Icon`, `Categories=Education;`, `StartupWMClass=system-design-from-scratch`) so the app is in the application menu. Replacing is a rename of a file written next to the target. It never needs `sudo`, never touches `~/.config/system-design-from-scratch/`, and refuses to replace a running instance (a process whose command line holds the path, or whose environment has `APPIMAGE=<path>`). When FUSE 2 is missing it prints the one-line fix and writes the launcher with `env APPIMAGE_EXTRACT_AND_RUN=1`, so the app starts anyway (slower); running the script again after installing `libfuse2` writes the normal launcher. The launcher path never changes, so the in-app update ([[#Linux updates (AppImage)]]) replaces the file under it. Uninstall: delete the install folder and the `.desktop` file.

Tests: `scripts/test-install.sh` (Linux branch; on a Mac the platform is faked with the test-only `SDFS_TEST_PLATFORM="Linux x86_64"`, documented in the header of `install.sh`, and the macOS branch runs for real with a signed fake app in a scratch folder), `shellcheck` (CI image and the Ubuntu container; not installed on the maintainer's Mac).

By hand, AppImage:

```bash
chmod +x system-design-from-scratch-0.1.0-x86_64.AppImage
./system-design-from-scratch-0.1.0-x86_64.AppImage
```

An AppImage mounts itself through FUSE 2: install `libfuse2t64` (Ubuntu 24.04; `libfuse2` on 22.04 and Debian 12) if it complains about FUSE. Without FUSE, `APPIMAGE_EXTRACT_AND_RUN=1 ./<file>.AppImage` extracts to a temporary folder and runs from there. The AppImage does not add a menu entry by itself (use a tool such as AppImageLauncher, or a `.desktop` file of your own).

deb:

```bash
sudo apt install ./system-design-from-scratch-0.1.0-amd64.deb
```

`apt` (not bare `dpkg -i`) pulls the dependencies. The app then starts from the application menu (Education) or with `system-design-from-scratch`. `sudo apt remove system-design-from-scratch` removes it; your data folder stays.

### glibc and Ubuntu 22.04

The oldest supported Linux release is **Ubuntu 22.04 LTS** (x64, glibc 2.35), the first real Linux user's machine. The CI runner (`ubuntu-latest`) is a newer Ubuntu (24.04, glibc 2.39), so what matters is what the *package* needs, not what it was built on.

Measured with `objdump -T` (`scripts/check-glibc.sh`) on the Electron 44.7.0 `linux-x64` binary (the version in `package.json`; the zip from the Electron release, SHA-256 checked against its `SHASUMS256.txt`):

| File | Highest glibc symbol version |
|---|---|
| `electron` (renamed `system-design-from-scratch`) | 2.25 |
| `chrome_crashpad_handler`, `libffmpeg.so`, `libvk_swiftshader.so` | 2.17 |
| `libvulkan.so.1` | 2.16 |
| `chrome-sandbox` | 2.4 |

So the package needs **glibc 2.25 or later** (Ubuntu 18.04 has 2.27, 20.04 has 2.31, 22.04 has 2.35, 24.04 has 2.39). There is no `GLIBCXX` or `CXXABI` requirement: Chromium bundles its own C++ library. The app has no native module (`node_modules` is not packaged), and the AppImage and deb builders run on the CI host without compiling anything, so the build host's glibc does not enter the package. The Electron binary links dynamically to GTK 3, NSS, ATK, CUPS, GBM, ALSA, D-Bus and X11 libraries (`libgtk-3.so.0`, `libnss3.so`, `libgbm.so.1`, `libasound.so.2`...), which Ubuntu 22.04 ships. A new Electron may raise the glibc requirement: the `linux` job runs `scripts/check-glibc.sh dist/linux-unpacked 2.35` and fails when it does.

What was checked (2026-10-16, a Docker container with Ubuntu 22.04.5, glibc 2.35, x64 emulated on an Apple Silicon machine, the libraries of the CI step installed with their 22.04 names, non-root user): `ldd` on the Electron binary finds every library; `electron --version` prints `v44.7.0`; the stock Electron app stays up for 25 seconds on `xvfb-run` (only D-Bus connection errors, the container has no bus); `scripts/test-install.sh` passes; and the packaged `app.asar` of this repository (built on macOS, it holds no native code) runs on that Linux binary through the smoke test with the default Chromium sandbox (setuid helper), including the AppImage update ([[#Smoke test]]).

What was **not** verified:

- **The AppImage file itself on Ubuntu 22.04**: it cannot be built from macOS, and the first CI run had not happened when this was written. The `linux-ubuntu-2204` job of the workflow does it on an `ubuntu-22.04` runner: it installs `libfuse2`, starts the downloaded AppImage (FUSE mount, DevTools port answers), then extracts it and runs the whole smoke test on the extracted app. electron-builder's AppImage runtime and `AppRun` script are not measured here (the runtime is a static binary).
- **A real GNOME desktop** (Wayland or X11): the launcher entry, its icon, the window grouping.
- Kernel and AppArmor settings of a real 22.04 desktop (user namespaces are unrestricted by default there, which the AppImage's Chromium sandbox needs; the restriction arrived with Ubuntu 24.04).
- If the `ubuntu-22.04` runner label is retired by GitHub, the job fails to start: replace it with a container or a newer oldest-supported release, and update this page.

### Chromium sandbox

The app keeps Chromium's process sandbox on (no `--no-sandbox` anywhere in the app code or the packaged launchers). On Linux Chromium sandboxes through one of two mechanisms:

- unprivileged user namespaces, when the kernel allows them;
- a setuid helper, `chrome-sandbox`, which must be owned by root with mode 4755.

What was seen: in an Ubuntu 24.04 container without user namespaces, the unpacked app aborts at startup with "The SUID sandbox helper binary was found, but is not configured correctly" until `chrome-sandbox` is `root:root` with mode 4755, and then runs with the default sandbox. Ubuntu 24.04 runners and desktops restrict unprivileged user namespaces with AppArmor (`kernel.apparmor_restrict_unprivileged_userns`), so the helper is the reliable way there.

- **CI smoke test**: electron-builder does not run as root and cannot set the bit, so the workflow runs `sudo chown root:root` and `sudo chmod 4755` on `dist/linux-unpacked/chrome-sandbox` before the smoke test. The smoke test prints which mechanism it found, and takes `--no-sandbox` (or `SMOKE_NO_SANDBOX=1`) only as an explicit opt-in for a machine that has neither, such as a container running as root. The workflow does not use it.
- **deb**: electron-builder's post-install script does it: it sets `chrome-sandbox` to 4755 when user namespaces do not work, keeps 0755 when they do, and installs an AppArmor profile (`/etc/apparmor.d/system-design-from-scratch`, `userns` allowed) on Ubuntu 24 and later. So the deb needs no flag.
- **AppImage**: it cannot use a setuid helper (the image is mounted without setuid), so it relies on user namespaces, and electron-builder's AppImage launcher adds no `--no-sandbox` (checked: no such switch on the running processes). On a system that restricts them (Ubuntu 24.04 default) it is expected to fail at startup with the same SUID message (not verified on such a system). Options, from most to least preferable: install the deb instead; allow user namespaces (`sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`, or an AppArmor profile for the AppImage); or start it with `--no-sandbox`, which turns Chromium's process sandbox off for the whole app and is the weakest choice. The app only loads its own bundled pages (the Content-Security-Policy and the navigation guards stay in place, see the README), which limits the exposure, but the choice is yours.

### Linux behavior of the app

- User data: `app.setPath('userData', <appData>/system-design-from-scratch)` in `src/main/index.ts`; on Linux `appData` is `~/.config` (or `$XDG_CONFIG_HOME`), so the folder is `~/.config/system-design-from-scratch/`, the same name logic as macOS (checked: a launch with a scratch `HOME` and no `--user-data-dir` created `$HOME/.config/system-design-from-scratch`).
- Quitting: closing the last window quits the app (`window-all-closed` calls `app.quit()` on every platform except macOS, which keeps the app in the Dock). The main process sets no macOS-only title bar style, and registers no custom menu, so Linux gets Electron's default menu bar.
- Claude Code CLI discovery on Linux: PATH, then `~/.claude/local`, `~/.local/bin` (the native installer's location, the one the smoke test uses), `/home/linuxbrew/.linuxbrew/bin`, `/usr/local/bin`, `~/.npm-global/bin`, the npm prefix, then a login shell lookup with `$SHELL`, else `/bin/bash` (`/bin/zsh` only on macOS). `src/main/generation/resolveCli.test.ts` covers `~/.local/bin` with a fake home and a minimal PATH, the login shell fallback (explicit shell and `$SHELL`), and the default shell per platform.

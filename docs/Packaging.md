# Packaging

How the macOS app (Apple Silicon, arm64, built locally) and the Linux app (x64 AppImage and deb, built in CI, see [[#Linux (x64)]]) are built from the repo with [electron-builder](https://www.electron.build/). Personal use: no signing identity, no notarization, no auto-update. Releases: [[#Releases]]. Context: [[Attribution and Licenses]] (what must travel with the app), [[SPEC]].

> [!warning] A package needs a tldraw license key
> Without a valid key at build time, the Design Canvas of the packaged app disappears 5 seconds after it opens. `npm run package` warns when the key is missing. See [[#tldraw license]] below, and [[#Smoke test]] for the automated check of a package.

## Build

Prerequisites: macOS on Apple Silicon, Node.js 22.18 or later, `npm ci` done, and the Electron binary installed (`npx install-electron`, run by `npm run dev` and `npm run preview`). No network is needed once Electron and the dmg tooling are in place.

```bash
npm run package       # electron-vite build, electron-builder (.app + .dmg), then the guard script
npm run package:dir   # same without the .dmg (faster, for checking the .app)
```

Output in `dist/` (git-ignored):

| Path | What |
|---|---|
| `dist/mac-arm64/System Design from Scratch.app` | The app, about 360 MB (Electron itself is most of it). |
| `dist/system-design-from-scratch-<version>-arm64.dmg` | Disk image with the app and an Applications shortcut, about 130 MB. |

The config is `electron-builder.yml`. Notes on the choices:

- `electronDist: node_modules/electron/dist`: the Electron already installed is packaged, nothing is downloaded for it. electron-builder still downloads its dmg tooling (`dmgbuild-bundle`) once, on the first `.dmg` build, into its cache; later builds are offline.
- `identity: null`: the app is not code-signed by electron-builder. The Electron binary from npm carries an ad-hoc linker signature and starts on Apple Silicon as is (checked).
- `npmRebuild: false`: the app has no native module (`node:sqlite` is built into Electron's Node).
- `publish: null`: no update feed (`latest-mac.yml`) is generated.
- The icons are generated by `npm run icon:build` (`scripts/build-icon.mjs`, run with Electron): the brand mark of the app header on a dark rounded square. It writes `build/icon.icns` (macOS, needs `iconutil`, so macOS only) and `build/icons/<size>x<size>.png` for 16, 24, 32, 48, 64, 128, 256 and 512 px (Linux). Rerun it and commit the result only when the design changes.

## What is in the package

`app.asar` holds `package.json`, `out/` (the electron-vite output: main, preload and the renderer with its inlined fonts and tldraw assets) and `resources/` (`corpus/primer.json`, `licenses.json`, `licenses/`). Nothing else: no `src/`, `docs/`, `spikes/`, `screenshots/`, `scripts/`, tests, `.env*`.

The app ships no `node_modules`. The renderer is bundled by Vite, and the main process bundle includes its only runtime package, `zod` (`electron.vite.config.ts`, `externalizeDeps.exclude`). A package added later to the main or preload side must be bundled too, or the guard script fails.

Outside the asar, in `Contents/Resources/`:

- `LICENSES.chromium.html`: the Chromium, Node.js and other notices that Electron distributes. Electron ships it next to `Electron.app`, not inside it, and electron-builder does not copy it into a macOS app, so `extraResources` does.
- `LICENSE.electron`: Electron's own MIT license.

### Guard script

`scripts/check-package.mjs [--platform mac|linux] [--app-only]` runs at the end of `npm run package` (macOS, the default platform) and `npm run package:linux`, and exits 1 when:

- `LICENSES.chromium.html` or the Electron license is missing from the `.app` (`Contents/Resources`) or, on Linux, from `dist/linux-unpacked/resources/`;
- `app.asar` lacks a runtime file (`out/main/index.js`, `out/preload/index.js`, `out/renderer/index.html`, `resources/corpus/primer.json`, `resources/licenses.json`) or contains an environment file (`.env`, `.env.local`...), a top-level `src`, `docs`, `spikes`, `screenshots`, `scripts`, `build`, `.github`, `.vitest` or `node_modules`, or a test file;
- the main or preload bundle requires a package other than Electron and Node built-ins;
- a tldraw license key is configured at build time but `app.asar` does not contain it (stale build), or the key shows up in the main or preload bundle (it belongs to the renderer only);
- there is no `.dmg` (macOS) or no `.AppImage` or `.deb` (Linux), or one is under 50 MB (not checked with `--app-only`, used by `package:dir` and `package:linux:dir`);
- on Linux, the Electron executable or `chrome-sandbox` is missing from `dist/linux-unpacked`.

The key itself is compared with the package, never printed. A package built without a key is valid for the guard script (see [[#tldraw license]]).

`scripts/check-tldraw-key.mjs` runs at the start and at the end of `npm run package`, `package:dir`, `package:linux` and `package:linux:dir` (so the message is not lost in the electron-builder output). It never fails the build.

## tldraw license

tldraw works in a production build only with a valid license key ([[tldraw|tldraw spike]], [[Design Canvas Integration#License key]], [[Attribution and Licenses#tldraw]]). A packaged app counts as production (`file://` origin, `NODE_ENV=production`).

### How the key flows

1. The key lives in `.env.local` at the repo root, as `VITE_TLDRAW_LICENSE_KEY=<key>` (git-ignored; `.env.example` documents the name). Never commit it, never paste it in an issue, a doc or a log.
2. At build time, `electron-vite build` (run by `npm run package` and `package:dir`) reads it through Vite's env loading in production mode. A `VITE_TLDRAW_LICENSE_KEY` set in the shell wins over `.env.local`; an empty value counts as no key.
3. Vite inlines it as a string in the renderer bundle (`out/renderer/assets/index-*.js`, then `app.asar`), and `DesignCanvas.tsx` passes it to `<Tldraw licenseKey>`. It is in no other file of the package: not in the main or preload bundles, and no `.env` file ships (`scripts/check-package.mjs` enforces both and checks that the key is in `app.asar`).
4. tldraw validates the key in the renderer, offline (a signed token, checked with the Web Crypto API). The key is client-side by design: anyone who has the `.app` can read it. tldraw says keys can be public, but do not publish a build that embeds yours.

`npm run package` and `npm run package:dir` print `tldraw license key found (N chars)` at the start and at the end of the build, or a warning when the variable is missing or empty. The build never fails for that. The value is never printed.

### A build without a key

Checked in the packaged app (2026-10-11, package built with the variable overridden to empty): nothing crashes. The canvas screen opens, then **5 seconds later tldraw stops rendering the editor** (`LICENSE_TIMEOUT` in `LicenseProvider.tsx`, state `unlicensed-production`): the drawing area turns blank, the component palette stays but its buttons are disabled, and a hidden `div[data-testid="tl-license-expired"]` replaces the editor. By its code, tldraw writes "No tldraw license key provided!" to the console. It is not only a watermark: the Design Canvas is unusable. The rest of the app (lessons, quizzes, About) is unaffected.

`npm run smoke:packaged` fails the check "tldraw stays rendered past its 5 s license gate" on such a package.

### Evaluation key and its expiry

The key in use is a 14-day tldraw **evaluation** key, received around 2026-10-09. Estimated expiry: **around 2026-10-23**. This is an estimate from the reception date: the exact date is inside the key (the last day is usable until the end of that day, UTC, and an evaluation key has no grace period). With an evaluation key tldraw enables every feature and shows no watermark.

When it expires, the packaged app behaves as with no key: the canvas disappears 5 seconds after it opens (state `expired`, same gate). Nothing is lost: the saved Design Scenes stay in the database. To find out in advance, run `npm run smoke:packaged` (its canvas check uses the current date, so it fails once the key has expired, without a rebuild).

### When the hobby key arrives

The hobby key request has had no answer yet (as of 2026-10-11). When it comes:

1. Replace the value of `VITE_TLDRAW_LICENSE_KEY` in `.env.local` (one line, no quotes needed).
2. `npm run package`: the log must say `tldraw license key found`.
3. `npm run smoke:packaged`: the canvas checks must pass.
4. Quit the app and replace it in `/Applications` ([[#Rebuild after a change]]). The data folder is untouched.
5. Expect the "made with tldraw" watermark on the canvas. The hobby license requires it to stay; nothing in the app hides it. The smoke test accepts it (it only rejects a missing, invalid or expired license).

The hobby key may be issued for specific hosts. The packaged renderer loads from `file://.../app.asar/out/renderer/index.html`, which has no hostname, so ask tldraw for a key that validates for that origin (their "native license" mode matches a protocol pattern against the page URL, see the spike). Step 3 tells you at once whether it does: a key that does not match the origin fails with "License key is not valid for this domain" in the console and the 5 second gate.

### Watermark tracking request

In a production build tldraw sends one request when the canvas opens, to `https://cdn.tldraw.com/5.5.2/watermarks/watermark-track.svg` with the query `version`, `license_type`, `license_id`, `sku` and `url` (the page URL: the local path of the app, with the macOS user name) and `environment=production`. Read in `LicenseManager.maybeTrack` of `@tldraw/editor@5.5.2`: it is sent for `unlicensed-production` (no key), for evaluation keys and for keys that show a watermark, so a hobby key too, although the license page says a hobby key sends nothing. It is not sent in development.

The renderer Content-Security-Policy (`connect-src 'self' data:`) blocks it on purpose: the app is offline by design. Seen in the packaged app: the editor keeps rendering, and Chromium logs two console errors per canvas open (a CSP violation and a failed `fetch`). The smoke test tolerates exactly those two, for `cdn.tldraw.com`, and fails on any other console error.

Whether blocking the request is acceptable under the license (it forbids interfering with license key enforcement) is not settled. The decision stays with the owner; the draft below is not sent.

> [!example] Draft message to tldraw (not sent)
> **Subject:** Hobby license for a personal offline desktop app: watermark tracking request
>
> Hello tldraw team,
>
> I am building a personal, non-commercial desktop app for learning system design (Electron, built for my own Mac, not distributed). It uses tldraw 5.5.2 for a diagram canvas. I requested a hobby license and I am running on an evaluation key meanwhile.
>
> Two questions, so that I stay within the license:
>
> 1. The packaged app loads from `file://`, with no hostname. Can the hobby key be issued so that it validates for that origin (for example as a native license matching the `file:` protocol)?
> 2. In production the SDK requests `https://cdn.tldraw.com/<version>/watermarks/watermark-track.svg` with the license id, the SKU and the page URL (a local path that contains my user name). The app is designed to run offline and its Content-Security-Policy (`connect-src 'self' data:`) blocks every remote request, so this one is blocked. The editor keeps rendering and the watermark stays visible. Is it acceptable that this request is blocked? If not, what do you recommend for an offline desktop hobby app?
>
> I would rather follow your recommendation than work around anything. Thank you for your time.
>
> [Name]


## Releases

Download page: GitHub Releases, linked from the README ([[#Download]] in the README). Issue #41.

Cut a release:

1. Bump `version` in `package.json` and `package-lock.json`, commit and push to `main`.
2. Tag and push: `git tag v<version> && git push origin v<version>`. The tag must equal `v` plus the `package.json` version, or the workflow stops.
3. `.github/workflows/package.yml` builds both packages (Linux on `ubuntu-latest`, macOS arm64 on `macos-14`), runs the guard script and the smoke test on each, then the `release` job creates a **draft** release named after the tag with the dmg, AppImage, deb and `SHA256SUMS` attached. The notes start from `.github/release-notes.md` (install steps), followed by GitHub's generated change list.
4. Open the draft on the Releases page, read it, then **Publish**. Nothing is public before that.

A manual run (**Actions > Package > Run workflow**) only uploads workflow artifacts (`linux-x64`, `macos-arm64`, 14 days), no release. A tagged build fails when the `VITE_TLDRAW_LICENSE_KEY` secret is missing: a release without it has a blank Design Canvas.

> [!warning] A public release exposes the tldraw license key
> The key is inlined in the renderer bundle ([[#How the key flows]]), so anyone who downloads a release can extract it. That is why the release is a draft. Before publishing, check that the key's terms allow it (the evaluation key is time-limited and not meant for distribution; the hobby key request is still open) and that it has not expired: a release built with an expired key opens with a Design Canvas that disappears after 5 seconds ([[#Evaluation key and its expiry]]).

Release assets have no space in their names (GitHub rewrites spaces to dots): electron-builder's `artifactName` is `${name}-${version}-${arch}.${ext}`.

Not verified: a release downloaded on a Mac carries the quarantine attribute ([[#Open an unsigned build]]); the macOS smoke test runs the app from the build folder, not from the downloaded dmg.

## User data

The packaged app uses the same folder as `npm run dev` and `npm run preview`: `~/Library/Application Support/system-design-from-scratch/` on macOS, `~/.config/system-design-from-scratch/` on Linux (`$XDG_CONFIG_HOME` when set; the SQLite database `system-design-from-scratch.db`, caches). The folder is named after the package name, not the product name ("System Design from Scratch"), so `src/main/index.ts` sets `userData` explicitly at startup unless a `--user-data-dir` switch is given (tests and verification runs use a scratch folder that way). Existing data is reused as is; a packaged app enforces the Learning Path locks that dev builds skip (`app.isPackaged`).

The app still needs the Claude Code CLI at runtime (see the README). An app opened from Finder (macOS) or from a Linux application menu or `.desktop` launcher does not see the shell PATH: it looks in the common install locations (`~/.local/bin`, `~/.claude/local`, Homebrew and Linuxbrew, `/usr/local/bin`, `~/.npm-global/bin`) and then asks a login shell (`$SHELL`, else bash on Linux). Set the CLI path in **Settings** if `claude` is still not found.

## Open an unsigned build

A package built locally has no quarantine attribute, so macOS opens it without a Gatekeeper prompt: drag the `.app` to `/Applications` (or open the `.dmg` and drag it onto the Applications shortcut), then open it.

A copy that was downloaded, AirDropped or sent by message gets the quarantine attribute and macOS refuses it as unverified. Either right-click the app, choose **Open**, then **Open** again; or remove the attribute:

```bash
xattr -dr com.apple.quarantine "/Applications/System Design from Scratch.app"
```

## Chromium license requirement

Chromium and the other bundled components require their license notices to be kept in every distribution. Electron provides them as `LICENSES.chromium.html`. Never strip it from a package; the guard script enforces it. The About screen lists the npm packages ([[Attribution and Licenses]]); this file covers Chromium and Node.js.

## Rebuild after a change

1. `npm run licenses:check` (after a `package-lock.json` change, `npm run licenses:build` first).
2. `npm run package` (check that the log says `tldraw license key found`, see [[#tldraw license]]).
3. `npm run smoke:packaged` ([[#Smoke test]]).
4. Replace the app in `/Applications` (quit it first). The data folder is untouched. For the first run of a new package, follow the [[#First launch checklist]].

To try a build without touching your data, launch the binary with a scratch folder: `"dist/mac-arm64/System Design from Scratch.app/Contents/MacOS/System Design from Scratch" --user-data-dir=/some/scratch/dir`.

## Smoke test

`npm run smoke:packaged` (`scripts/smoke-packaged.mjs`, plain Node, no dependency) drives the packaged app the way a Finder launch would, as far as a script can. It is platform aware: on macOS it runs `dist/mac-arm64/System Design from Scratch.app`, on Linux `dist/linux-unpacked/system-design-from-scratch` (under `xvfb-run -a`, see [[#Linux (x64)]]). Run it after `npm run package`, `package:dir`, `package:linux` or `package:linux:dir`; it takes about 15 seconds. Options: `--app <binary>` (another build), `--shots <dir>` (keep the screenshots, default: inside the scratch folder), `--keep` (keep the scratch folder), `--no-sandbox` (Linux, see below), and `SMOKE_VERBOSE=1` (print the console messages of the canvas screen).

How it runs:

- The app binary is spawned with `--remote-debugging-port=<free port>`, a scratch `--user-data-dir` (always passed, so the real user data is never opened) and a **minimal environment**: `PATH=/usr/bin:/bin`, no `SHELL`, and `HOME` set to a scratch folder (on Linux, `DISPLAY` and `XAUTHORITY` are passed through: Chromium needs a display). The real user data and `~/.claude*` are never touched.
- A fake Claude Code CLI sits in `<scratch HOME>/.local/bin/claude`. It speaks the stream-json protocol the app expects (`--version`, `auth status`, a Notion Outline, a lesson with a Mermaid flowchart) and logs every call. As `claude` is not on PATH, finding it proves the discovery through the common install locations (`commonCliLocations` in `src/main/generation/resolveCli.ts`) and the stream-json plumbing of a packaged app.
- The page is driven over the Chrome DevTools protocol (the WebSocket built into Node 22+).
- Two launches share one scratch user-data folder. The first starts on a fresh folder. Then the app is stopped, every topic is marked mastered in the scratch database (with `node:sqlite`; the app cannot be imported here, so the script inserts a passed round per topic, the way the earlier seed scripts did) and the app is launched again, because a packaged app enforces the Learning Path lock and an exercise opens only when its prerequisites are mastered.
- The whole process group of the app is killed at the end, also on failure or Ctrl+C. The script exits 1 when a check fails and prints one `PASS`/`FAIL` line per check. It never prints the tldraw key.

Covered:

| Check | What it proves |
|---|---|
| Window loads, `file:` origin | The packaged renderer starts, the preload bridge works. |
| Learning Path shows 21 topics | The Source Corpus is read from the package (`resources/corpus/primer.json` in the asar). |
| Database created and migrated | Scratch folder has `system-design-from-scratch.db` at the latest schema version, 21 topics and the Design Exercises seeded. |
| Settings, Test button | The screen renders, the CLI is found in `~/.local/bin` without PATH, version and login state shown. |
| About | `licenses.json` is readable (374 entries), the tldraw section and the primer attribution render. |
| Fonts | Geist is loaded (`document.fonts`), the fonts inlined in the bundle work from `file://`. |
| First lesson | Generated by the fake CLI through the packaged main process, displayed, the CLI got the request. |
| Mermaid diagram | The lesson's flowchart is rendered as SVG (no fallback to the source). |
| Exercise canvas | After the topics are mastered, the first exercise opens on its Design Canvas, tldraw stays rendered after its 5 second license gate, with no license message, with its 37 bundled icons and fonts, and a typed shape can be added. |
| Console | No console error on the first launch. On the canvas screen, the only one tolerated is tldraw's blocked tracking request ([[#Watermark tracking request]]). |

Not covered, to check by hand ([[#First launch checklist]]):

- **The real Claude Code CLI**: login, models, real latency and output, the Claude config directory. The fake CLI proves the plumbing, not the content.
- **The real network**: nothing is fetched (the CSP forbids it), and no check runs online.
- **Gatekeeper and quarantine on a downloaded copy**: the locally built `.app` has no quarantine attribute ([[#Open an unsigned build]]).
- **A launch through LaunchServices** (Finder, Dock, `open`): the script starts the binary directly, with an environment that imitates it. launchd's own environment, the app icon, the window state and the single-instance behavior are not exercised.
- The `.dmg` itself (never mounted), the copy in `/Applications`, Intel Macs, light mode, and the quality of the generated French content.

A failure keeps the scratch folder and prints its path and the app output.

## First launch checklist

For the first run of a new package on your Mac (after `npm run package` and a passing `npm run smoke:packaged`):

1. Quit the running app if any. Copy `dist/mac-arm64/System Design from Scratch.app` (or the `.app` from the `.dmg`) to `/Applications`, replacing the old one. If the copy came from a download or a message, clear the quarantine attribute first ([[#Open an unsigned build]]).
2. Open it from `/Applications` (Finder or Spotlight, not from a terminal: that is the case the smoke test cannot reproduce). The Learning Path shows 21 topics and your previous progress.
3. **Settings**: leave the CLI path empty and press **Test**. Expect the CLI version, its path and your login state. If it says `claude` is not found, set the path (`which claude` in a terminal) and test again.
4. Open an unlocked topic and read one generated **lesson** to the end: text streams in, a Mermaid diagram renders.
5. Take one **quiz round**: answer a few questions, including a free answer if the round has one.
6. During the round, press the **Lesson** button: the lesson opens and closes without losing the round.
7. **Design exercise**: once the prerequisites of Pastebin are mastered, open it, go to **High-level design**, add a component with the palette, and leave the screen open for more than 5 seconds: the canvas must stay, with no license message (a "made with tldraw" watermark is expected with a hobby key). The exercise stays locked until its topics are mastered, so this step may have to wait; do not edit your real database to unlock it.
8. **About**: the tldraw license text and the third-party licenses are listed.

## Linux (x64)

The Linux app is an AppImage and a `.deb` for x64, built by GitHub Actions on an Ubuntu runner (`.github/workflows/package.yml`), never cross-built from macOS: the Electron binary packaged is the one in `node_modules`, which is the Linux one only on a Linux host. Unsigned, no auto-update, personal use (issue #40).

### Build in CI

Run **Actions > Package > Run workflow** on GitHub (or `gh workflow run package.yml`), or push a `v*` tag. The workflow has read-only permissions and one job, `linux`, on `ubuntu-latest`:

1. `actions/checkout`, `actions/setup-node` (Node 24, npm cache) and `npm ci`, the same pinned versions as `ci.yml`.
2. System libraries (`apt-get`): `xvfb` and `xauth` (virtual display), `libfuse2t64` (runs an AppImage without extracting it), `binutils` (`ar`, needed by the deb builder), and what the Electron binary links against: `libnss3`, `libgtk-3-0t64`, `libatk1.0-0t64`, `libatk-bridge2.0-0t64`, `libcups2t64`, `libgbm1`, `libasound2t64`, `libdrm2`, `libxss1`, `libxtst6`, `libxkbcommon0`, `libxcomposite1`, `libxdamage1`, `libxfixes3`, `libxrandr2`, `libpango-1.0-0`, `libcairo2`, `xdg-utils`. Most are already on the runner image; the names are the Ubuntu 24.04 ones (`t64` suffix).
3. `npm run package:linux`: `install-electron` (downloads the Electron binary, `npm ci` does not), the tldraw key report, `electron-vite build`, `electron-builder --linux --x64`, the guard script (`node scripts/check-package.mjs --platform linux`), the key report again. The key comes from the repository secret `VITE_TLDRAW_LICENSE_KEY` (set in **Settings > Secrets and variables > Actions**), passed as the environment variable of that step only. GitHub masks it in logs and no script prints it. The guard script runs once more as its own step.
4. The sandbox helper step ([[#Chromium sandbox]]).
5. `xvfb-run -a npm run smoke:packaged -- --shots smoke-shots` ([[#Smoke test]]): the app launched from `dist/linux-unpacked` on a virtual display, with the minimal environment and the fake CLI.
6. `actions/upload-artifact`: the artifact `linux-x64` holds `dist/*.AppImage` and `dist/*.deb`, kept 14 days. If the smoke test fails, the screenshots go up as the artifact `smoke-shots` and the packages are not uploaded.

Without the secret the job still runs: it prints a warning annotation, the build prints the no-key warning ([[#tldraw license]]), and the smoke test skips its three tldraw checks (`SMOKE_ALLOW_MISSING_TLDRAW_KEY`, set by the workflow only in that case), because the Design Canvas of such a package is blank after 5 seconds. That package is not fit to use. With a key, nothing is skipped.

Download the files from the run page (**Artifacts**), or `gh run download <run id> -n linux-x64`. The key is inlined in the renderer bundle ([[#How the key flows]]), so artifacts of a private repository are fine to keep, but do not publish them.

### Build on a Linux machine

`npm ci`, then `npm run package:linux` (or `npm run package:linux:dir` for `dist/linux-unpacked` only, no installable). Needs Node 22.18+, the libraries above for the smoke test, and `binutils` for the `.deb`. electron-builder downloads its AppImage runtime (`appimage-*.7z`) and the fpm bundle (`.deb`) once into its cache. The fpm bundle it downloads for the `.deb` is an x64 build (not tried on an arm64 host).

Output in `dist/`:

| Path | What |
|---|---|
| `dist/system-design-from-scratch-<version>-x86_64.AppImage` | AppImage, about 130 MB. |
| `dist/system-design-from-scratch-<version>-amd64.deb` | Debian package, about 105 MB. |
| `dist/linux-unpacked/` | The unpacked app: executable `system-design-from-scratch`, `chrome-sandbox`, `resources/app.asar`. |

### Config notes (`linux` in `electron-builder.yml`)

- Targets `AppImage` and `deb`, x64 only; category `Education`; the same `files` rules as macOS (the asar holds `package.json`, `out/`, `resources/`, no `node_modules`).
- `artifactName` is `${name}-${version}-${arch}.${ext}`, so the file names have no space (a `.deb` is installed with `apt install ./<file>`, a name with spaces is awkward). The macOS name keeps the product name.
- Licenses: `extraResources` copies `LICENSE.electron` and `LICENSES.chromium.html` into `resources/`, as on macOS, and the guard script requires them there. The Electron distribution also leaves `LICENSES.chromium.html` and `LICENSE.electron.txt` next to the executable; electron-builder keeps them, so the package holds both copies (about 20 MB more).
- Icons: `build/icons/*.png`, from `npm run icon:build` ([[#Build]]). The deb installs them in the `hicolor` theme and a `.desktop` file (`Name`, `Categories=Education`, `StartupWMClass=system-design-from-scratch`).
- `package.json` carries what the Linux targets read: `homepage` (the deb builder refuses to run without it), `author` (name only: an email is not required, the deb `maintainer` is set in the yml), and `desktopName` with `linux.syncDesktopName: true`, so that Electron's window class matches the `.desktop` file and the launcher groups the window under its icon.
- The `.deb` installs in `/opt/System Design from Scratch/` (the product name, with spaces), links `/usr/bin/system-design-from-scratch`, depends on `libgtk-3-0`, `libnss3`, `libxss1`, `libxtst6`, `libatspi2.0-0`, `libsecret-1-0` and a few more, and recommends `libappindicator3-1`.

### Install

AppImage:

```bash
chmod +x system-design-from-scratch-0.1.0-x86_64.AppImage
./system-design-from-scratch-0.1.0-x86_64.AppImage
```

An AppImage mounts itself through FUSE 2: install `libfuse2t64` (Ubuntu 24.04; `libfuse2` on 22.04 and Debian 12) if it complains about FUSE. Without FUSE, `APPIMAGE_EXTRACT_AND_RUN=1 ./<file>.AppImage` extracts to a temporary folder and runs from there. The AppImage does not add a menu entry by itself (use a tool such as AppImageLauncher, or a `.desktop` file of your own).

deb:

```bash
sudo apt install ./system-design-from-scratch-0.1.0-amd64.deb
```

`apt` (not bare `dpkg -i`) pulls the dependencies. The app then starts from the application menu (Education) or with `system-design-from-scratch`. `sudo apt remove system-design-from-scratch` removes it; your data folder stays.

### Chromium sandbox

The app keeps Chromium's process sandbox on (no `--no-sandbox` anywhere in the app code or the packaged launchers). On Linux Chromium sandboxes through one of two mechanisms:

- unprivileged user namespaces, when the kernel allows them;
- a setuid helper, `chrome-sandbox`, which must be owned by root with mode 4755.

What was seen: in an Ubuntu 24.04 container without user namespaces, the unpacked app aborts at startup with "The SUID sandbox helper binary was found, but is not configured correctly" until `chrome-sandbox` is `root:root` with mode 4755, and then runs with the default sandbox. Ubuntu 24.04 runners and desktops restrict unprivileged user namespaces with AppArmor (`kernel.apparmor_restrict_unprivileged_userns`), so the helper is the reliable way there.

- **CI smoke test**: electron-builder does not run as root and cannot set the bit, so the workflow runs `sudo chown root:root` and `sudo chmod 4755` on `dist/linux-unpacked/chrome-sandbox` before the smoke test. The smoke test prints which mechanism it found, and takes `--no-sandbox` (or `SMOKE_NO_SANDBOX=1`) only as an explicit opt-in for a machine that has neither, such as a container running as root. The workflow does not use it.
- **deb**: electron-builder's post-install script does it: it sets `chrome-sandbox` to 4755 when user namespaces do not work, keeps 0755 when they do, and installs an AppArmor profile (`/etc/apparmor.d/system-design-from-scratch`, `userns` allowed) on Ubuntu 24 and later. So the deb needs no flag.
- **AppImage**: it cannot use a setuid helper (the image is mounted without setuid), so it relies on user namespaces, and electron-builder's AppImage launcher adds no `--no-sandbox` (checked: no such switch on the running processes). On a system that restricts them (Ubuntu 24.04 default) it is expected to fail at startup with the same SUID message (not verified on such a system). Options, from most to least preferable: install the deb instead; allow user namespaces (`sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`, or an AppArmor profile for the AppImage); or start it with `--no-sandbox`, which turns Chromium's process sandbox off for the whole app and is the weakest choice. The app only loads its own bundled pages (the Content-Security-Policy and the navigation guards stay in place, see the README), which limits the exposure, but the choice is yours.

### Linux behavior of the app

- User data: `app.setPath('userData', <appData>/system-design-from-scratch)` in `src/main/index.ts`; on Linux `appData` is `~/.config` (or `$XDG_CONFIG_HOME`), so the folder is `~/.config/system-design-from-scratch/`, the same name logic as macOS (checked: a launch with a scratch `HOME` and no `--user-data-dir` created `$HOME/.config/system-design-from-scratch`).
- Quitting: closing the last window quits the app (`window-all-closed` calls `app.quit()` on every platform except macOS, which keeps the app in the Dock). The main process sets no macOS-only title bar style, and registers no custom menu, so Linux gets Electron's default menu bar.
- Claude Code CLI discovery on Linux: PATH, then `~/.claude/local`, `~/.local/bin` (the native installer's location, the one the smoke test uses), `/home/linuxbrew/.linuxbrew/bin`, `/usr/local/bin`, `~/.npm-global/bin`, the npm prefix, then a login shell lookup with `$SHELL`, else `/bin/bash` (`/bin/zsh` only on macOS). `src/main/generation/resolveCli.test.ts` covers `~/.local/bin` with a fake home and a minimal PATH, the login shell fallback (explicit shell and `$SHELL`), and the default shell per platform.

### What was checked, and what was not

Checked on 2026-10-11 in a Docker container (Ubuntu 24.04, x64 emulated on an Apple Silicon machine, Node 24, non-root user, `xvfb-run`): `npm ci`, `npm run package:linux` (AppImage, deb, guard script), the smoke test against `dist/linux-unpacked` with the setuid sandbox helper (12 checks: window, Learning Path, database, Settings with the fake CLI found in `~/.local/bin` without PATH, About, fonts, a lesson with a Mermaid diagram, relaunch, exercise canvas), `sudo apt install ./<deb>` (accepted, files and `.desktop` entry in place), and the AppImage started with `APPIMAGE_EXTRACT_AND_RUN=1` (the window loaded and the DevTools port answered). That run had no real tldraw key, so the three tldraw checks were skipped, not passed. The first CI run is the real check; its result is reported in issue #40.

Not verified:

- **A real desktop**: Wayland, a window manager, the launcher icon and window grouping, the menu bar look, and the Education menu entry. The smoke test runs on xvfb, with no GPU.
- **The real Claude Code CLI** on Linux (login, models, the config directory), and the real network. The fake CLI proves the plumbing, as on macOS.
- **tldraw on Linux with a valid key**: the canvas checks pass only on a package built with a key. They are expected to behave as on macOS (same renderer code), but the first CI run with the secret is what proves it.
- **The AppImage on a system that restricts user namespaces**, and the AppImage with FUSE (the container had no FUSE).
- **Other distributions, Intel and arm64 hosts other than x64**, and the first CI run result.
